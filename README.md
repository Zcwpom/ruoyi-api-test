# 若依（RuoYi-Vue）接口测试项目

拿开源的若依后台管理系统当被测系统，练了一遍接口测试的完整流程：
看接口文档 → 设计用例 → 写断言 → 找问题 → 提缺陷单 → 做自动化回归。

| 项目 | 数值 |
| --- | --- |
| 被测系统 | RuoYi-Vue v3.9.2（Spring Boot + Spring Security + JWT） |
| 覆盖范围 | 5 大模块、37 个接口 |
| 断言数量 | 110 条（实跑 109 条，有 1 条因为验证码关掉了没执行） |
| 发现的问题 | 7 个（高危 1 / 中 3 / 低 3），其中 3 个写了正式报告 |
| 全量回归 | Newman 命令行，6 秒出 HTML 报告 |
| 性能测试 | JMeter 压登录链路，定位到瓶颈 |
| 用到的工具 | Postman、Newman、JMeter、MySQL、Redis、Git |

## 一、主要做了什么

### 1. 集合分层，鉴权统一配

集合按模块分成 5 个文件夹（登录鉴权 / 用户管理 / 系统管理 / 监控运维 / 通用能力）。
鉴权统一配在集合根节点上，只有登录接口单独设成不用鉴权 —— 新加接口不用一个个配请求头。

### 2. 加了自动登录，不然 token 一过期就全红

一开始必须先手动跑一遍登录，不然其他接口全是 401。后来在集合级的 Pre-request 里
加了判断：本地没有 token、或者快过期了，就先调一次登录接口拿新的。

后面又发现两种情况也会 401：

- **「退出登录」和「强退在线用户」本身就会让会话失效** —— 所以这两个用例跑完之后，
  主动把本地 token 清掉
- **服务端把 token 作废了（比如 Redis 重启），本地还留着** —— 所以集合级又加了一层：
  收到 401 就清掉 token、重跑一次当前请求

现在 37 条用例从哪一条开始跑都行，不用管顺序。

### 3. 断言分了几层

- HTTP 状态码是不是 200
- 业务 code 是不是 200（若依把错误放在业务 code 里，**HTTP 永远是 200**）
- 返回结构对不对（有没有 total、rows）
- 字段类型对不对
- 响应时间有没有超标

「不该泄露内部信息」这类，直接断言响应里不能出现某些内容：

```js
pm.expect(body).to.not.match(/com\.ruoyi|SysUser|java\.lang/);
```

### 4. 缺陷回归用例：断言「修好之后应该是什么样」

`91 已知缺陷回归` 文件夹里的用例，是给已经提了单的缺陷做的回归。断言写的是期望的
正确行为，所以现在是**红灯**；等修好了会自动变绿，不用改用例。

主套件（00~04）保持全绿，91 单独一个文件夹放。跑的时候可以只跑主套件，
也可以一起跑、允许这 7 条红灯（相当于已知问题清单）。

**这里踩过一个坑**：D9 的回归断言本来写的是 `code ≠ 200`。它现在确实是绿的，
但绿的**原因是「SQL 报错了」**，不是「参数校验生效了」。而且按缺陷报告里建议的修法
（非法值当 asc 处理），修好之后 code 会变成 200，这条断言**反而会变红**。

后来改成了条件断言：

```js
if (json.code !== 200) {
  pm.test("[缺陷009] 若返回错误，提示必须可读", () => {
    pm.expect(String(json.msg)).to.match(/[\u4e00-\u9fa5]/);
  });
}
```

**结论：回归断言只能写「修完之后一定会成立」的东西，不能把某一种修法写死。**

### 5. 用 Newman 在命令行跑

```bash
newman run postman/RuoYi-Vue.postman_collection.json \
  -e postman/RuoYi-Local.postman_environment.json \
  --timeout-request 10000 \
  -r "cli,htmlextra" \
  --reporter-htmlextra-export report/ruoyi-api-report.html
```

两个踩过的点：

- PowerShell 里 `-r cli,htmlextra` **要加引号**，不然逗号会被当成数组，
  Newman 会去找一个叫 "cli htmlextra" 的报告器然后报错
- 文件上传的用例在 Postman 界面里一直发不出去（服务端收到 null），换成 Newman
  就正常了 —— 命令行会直接按集合里记的路径读文件，界面版不会

### 6. 用 JMeter 压了登录链路

功能测试只能证明「对不对」，证明不了「快不快、扛不扛得住」。
链路是 `/captchaImage` → `/login` → `/getInfo`，脚本里做了关联（JSONPath 取 token）、
参数化（CSV 驱动两个账号）、事务控制。

**阶梯加压（5 秒爬升 / 15 秒持续）：**

| 并发 | TPS | 平均响应 | 错误率 |
| --- | --- | --- | --- |
| 10 | 119.6 | 71 ms | 0.00% |
| 20 | 137.3 | 121 ms | 0.00% |
| 50 | 146.0 | 282 ms | 0.00% |
| 100 | 152.1 | 538 ms | 0.00% |

并发涨了 9 倍、TPS 只涨 27%，响应时间却涨了 658% —— **新增的并发基本都变成排队了**，
据此判断容量上限约 20 并发。

**单接口隔离压测（50 并发）定位瓶颈：**

| 被测接口 | TPS | 平均响应 |
| --- | --- | --- |
| GET /captchaImage | **25,324** | 1 ms |
| POST /login | **42.1** | **990 ms** |

验证码接口能跑到 2.5 万 TPS，说明 Web 容器和网络层没问题；而登录接口在 10 并发
（201 ms）和 50 并发（990 ms）下吞吐几乎不变、响应时间翻了 5 倍，说明登录链路上
有个串行化的东西卡着。响应时间分布很集中 —— 判断是 **BCrypt 密码校验的 CPU 密集计算**
（若依用 `BCryptPasswordEncoder`，为了抗暴力破解刻意设计成慢的）。

所以优化方向是**水平扩容**，不是降低加密强度。

> ⚠️ 这次是单机压测（JMeter 和被测系统在同一台机器上），压力机自己也吃 CPU，
> 测出来的容量偏保守，主要用来做横向对比和瓶颈定位，不是绝对值。

完整报告：[jmeter/性能测试报告-若依.md](jmeter/性能测试报告-若依.md)

### 7. 用例是怎么设计的

每个接口从这几个方向想测试点，不只是测「能不能通」：

| 方向 | 具体想什么 |
| --- | --- |
| 鉴权 | 不带 token、token 是假的、权限不够、只能看自己部门的数据 |
| 参数 | 必填不传、类型传错、边界值（0、-1、特别大）、超长、特殊字符、注入 |
| 业务规则 | 状态值合不合法、时间范围能不能反过来、唯一性 |
| 数据一致性 | total 和 rows 对不对得上、列表和详情一样吗、改完再查一遍 |
| 组合 | 多个条件一起传会怎样 |
| 副作用 | 会不会影响别的数据、要不要善后 |
| 性能 | 响应时间、重复提交会怎样 |

## 二、发现的问题

| 编号 | 问题 | 严重程度 | 状态 |
| --- | --- | --- | --- |
| **D9** | 排序参数 isAsc 没做校验，传非法值会让接口把**完整 SQL 语句、服务器路径**返回给客户端 | **高** | [报告](缺陷报告-D9-isAsc未校验导致SQL信息泄露.md) |
| **D1** | 查一个不存在的用户，返回的是 Java 异常信息，里面有包名、类名 | 中 | [报告](缺陷报告-D1-用户详情NPE信息泄露.md) |
| D3 | 查询时间范围传反了（开始晚于结束），不报错，直接返回全部数据 | 中 | 已记录 |
| D4 | 查询时间格式写错，被忽略掉，也是返回全部数据 | 中 | 已记录 |
| D5 | pageSize 传 100000 也能执行，没有上限 | 中 | 已记录 |
| **D7** | 分页参数传非数字不报错、静默按默认值处理；但同一个模块的 userId 传非数字会明确报错，两套策略不一致 | 低 | [报告](缺陷报告-D7-分页参数静默降级.md) |
| D2 | 用 authRole 接口查不存在的用户，返回 code=200 还带 user:null | 低 | 已记录 |

**另外验证通过的几项：**

| 检查项 | 结果 |
| --- | --- |
| SQL 注入 `userName=' or '1'='1` | ✅ 返回空列表，没被注入 |
| 排序字段注入 `orderByColumn=1,(select 1)` | ✅ 被拦截，提示"参数不符合规范" |
| 不带 token 访问 | ✅ 返回 401 |
| 用普通角色 ry 查别人的数据 | ✅ 只能看到自己的 |

> D9 那条缺陷的预期依据就是从第 2 项来的：同一个 ORDER BY 的位置上，
> `orderByColumn` 防住了，`isAsc` 完全没防。

## 三、怎么跑起来

### 环境要求

JDK 17+ / MySQL 5.7+ / Redis 3.0+ / Node.js 14+ / Postman 12.x / Newman 6.x

### 启动被测系统

```bash
git clone https://gitee.com/y_project/RuoYi-Vue.git
# 建库 ry-vue，导入 sql/ 目录下的两个 sql 文件
# 改 application-druid.yml（数据库密码）和 application.yml（ruoyi.profile 上传目录）
mvn clean package -DskipTests
java -jar ruoyi-admin/target/ruoyi-admin.jar
```

关掉验证码，不然自动化登录会失败：

```sql
UPDATE sys_config SET config_value = 'false' WHERE config_key = 'sys.account.captchaEnabled';
```

### 跑自动化

```bash
npm install -g newman newman-reporter-htmlextra

newman run postman/RuoYi-Vue.postman_collection.json \
  -e postman/RuoYi-Local.postman_environment.json \
  --timeout-request 10000 \
  -r "cli,htmlextra" \
  --reporter-htmlextra-export report/ruoyi-api-report.html
```

跑出来大概是：

```
requests           39     failed 0
assertions        109     failed 7
total run duration: 6s
```

那 7 条失败就是 `91` 文件夹里的，对应上面 3 个缺陷，属于预期内。

## 七、关于仓库里的信息

报告和截图里包含本地测试环境的一些信息，说明一下：

- **HTML 报告里的 token**：针对 `http://localhost:8080` 生成的，默认 30 分钟过期，
  现在已经失效，对别人没用
- **内网 IP**：本机网卡地址，10.x 是私有网段，公网访问不到
- **admin / admin123**：若依官方文档里公开的默认账号密码，不是真实凭证
- **本机路径**：D9 缺陷报告里那处路径是**接口泄露出来的内容本身**，属于缺陷证据

真实项目里这些都要脱敏。这里因为是完全本地的练习环境，所以保留了原始数据，
方便别人对照复现。
